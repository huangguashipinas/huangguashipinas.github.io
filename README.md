# gent 上下文预算管理器：三级压缩与缓存命中验证 
这篇教你给 Agent 装一个「上下文预算管理器」：把系统提示词、工具定义、对话尾部按层装配，超出预算时按卸载 → 摘要 → 丢弃三级依次压缩，同时保证压缩动作绝不踩坏可缓存的前缀。最终你会得到一个零依赖、能直接跑的 Python 模块，外加一段用来判断缓存到底命中没有的探针脚本。

适用环境：Python 3.11+，不需要 GPU；主示例完全离线可跑，缓存探针部分需要一个支持 cache_control 的模型账号和 API Key。

先说清楚：为什么「窗口够大」不等于「不用管」
模型上下文窗口这两年涨得很快，很多团队因此把「上下文管理」这件事往后放了。但只要你在跑 Agent，迟早会撞上三个问题，而它们跟窗口多大没关系：

钱。Agent 的每一轮都要把系统提示词和工具定义重发一遍。窗口 20 万 token 不代表你每轮都该发 20 万，重复的前缀按全价计费，一次任务几十轮下来，账单会非常难看。
延迟。首 token 时间跟输入长度基本同向增长。同一件事，前缀从 8 千 token 压到 2 千，交互手感是两个档次。
质量。上下文越长，中段信息被稀释得越厉害。这不是玄学，是长上下文任务里普遍观察到的现象：关键约束夹在几千 token 的日志中间，模型漏掉的概率明显上升。
所以预算管理不是「塞不下了才做的兜底」，而是每一轮都要做的决策。这篇的落点就是把这个决策写成代码。

设计：四层结构 + 一个断点
把一次请求的输入拆成四层，顺序固定，越靠前越稳定：

层	内容	跨轮是否稳定	能否压缩
system	角色、规则、禁止项	稳定（基本不变）	不建议压，压了会改行为
tools	工具名、描述、参数 schema	稳定	不建议压，压了模型可能调错
brief	任务背景、参考文档片段	半稳定	可以换更短版本
transcript	多轮对话 + 工具返回结果	每轮都在变	主要压缩对象
规则只有一条：缓存断点必须落在最后一个稳定层的末尾，也就是 brief 之后、transcript 之前。断点之前的内容逐字节不变，缓存才可能命中；一旦你在断点前塞了时间戳、随机 id、或者每轮改一次的工具清单，缓存就是永远不命中的。

这个约束会反过来约束你的代码设计：压缩逻辑只能碰 transcript，别的层一律不许动。下面每一处实现都在守这条线。
